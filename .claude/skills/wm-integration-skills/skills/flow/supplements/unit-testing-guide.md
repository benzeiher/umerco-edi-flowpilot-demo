# webMethods Unit Testing Guide

## Overview

This guide explains how to create and structure unit tests for webMethods services generated by the wm-flow-pilot skill. Unit tests use the webMethods XML-based testing framework with IDataXMLCoder format.

---

## When to Generate Unit Tests

Unit tests should be generated:
- ✅ When explicitly requested by the user
- ✅ After Bob prompts: "Would you like me to generate unit tests for this service?"
- ❌ NOT automatically with every service generation

---

## Test Suite Structure

Each test suite consists of three types of files:

### 1. Test Suite XML (`[ServiceName]_TestSuite.xml`)
Defines all test cases for a service.

### 2. Input XML Files (`[testName]-input.xml`)
Contains input parameters for each test case.

### 3. Result XML Files (`[testName]-result.xml`)
Contains expected output values for each test case.

---

## Directory Organization

Tests are organized in a `tests/` subdirectory within the service folder:

```
output/
  [ServiceName]/
    [ServiceName].flow
    [ServiceName].md (optional)
    tests/
      [ServiceName]_TestSuite.xml
      [testName]-input.xml
      [testName]-result.xml
```

**Example:**
```
output/
  addTwoNumbers/
    addTwoNumbers.flow
    addTwoNumbers.md
    tests/
      addTwoNumbers_TestSuite.xml
      success_test1-input.xml
      success_test1-result.xml
      error_test1-input.xml
      error_test1-result.xml
```

---

## Test Suite XML Format

### Basic Structure

```xml
<?xml version="1.0" encoding="UTF-8"?>
<webMethodsTestSuite description="[ServiceName] TestSuite" name="[serviceName]TestSuite">
    <webMethodsTestCase description="[Test Description]" name="[testName]">
        <service folder="[packageFolder]" name="[ServiceName]">
            <input>
                <file filename="tests/[testName]-input.xml"/>
            </input>
            <expected>
                <file filename="tests/[testName]-result.xml"/>
            </expected>
        </service>
    </webMethodsTestCase>
</webMethodsTestSuite>
```

> **Note**: The `filename` attribute must include the `tests/` folder prefix. The path is relative to the service folder (i.e., the folder containing the `.flow` file), not relative to the TestSuite XML file itself.

### Multiple Test Cases

```xml
<?xml version="1.0" encoding="UTF-8"?>
<webMethodsTestSuite description="addTwoNumbers TestSuite" name="addTwoNumbersTestSuite">
    <webMethodsTestCase description="Success Test: 5 + 3 = 8" name="success_test1">
        <service folder="services" name="addTwoNumbers">
            <input>
                <file filename="tests/success_test1-input.xml"/>
            </input>
            <expected>
                <file filename="tests/success_test1-result.xml"/>
            </expected>
        </service>
    </webMethodsTestCase>
    <webMethodsTestCase description="Error Test: Invalid input" name="error_test1">
        <service folder="services" name="addTwoNumbers">
            <input>
                <file filename="tests/error_test1-input.xml"/>
            </input>
            <expected>
                <file filename="tests/error_test1-result.xml"/>
            </expected>
        </service>
    </webMethodsTestCase>
</webMethodsTestSuite>
```

## IDataXMLCoder Format

All input and result files use the webMethods IDataXMLCoder format.

### Simple Values

```xml
<?xml version="1.0" encoding="UTF-8"?>
<IDataXMLCoder version="1.0">
  <record javaclass="com.wm.data.ISMemDataImpl">
    <value name="paramName">paramValue</value>
    <value name="anotherParam">anotherValue</value>
  </record>
</IDataXMLCoder>
```

### Nested Records

```xml
<?xml version="1.0" encoding="UTF-8"?>
<IDataXMLCoder version="1.0">
  <record javaclass="com.wm.data.ISMemDataImpl">
    <record name="customer" javaclass="com.wm.data.ISMemDataImpl">
      <value name="id">123</value>
      <value name="name">John Doe</value>
      <value name="email">john@example.com</value>
    </record>
  </record>
</IDataXMLCoder>
```

### Arrays/Lists

```xml
<?xml version="1.0" encoding="UTF-8"?>
<IDataXMLCoder version="1.0">
  <record javaclass="com.wm.data.ISMemDataImpl">
    <array name="users" type="record" depth="1">
      <record javaclass="com.wm.data.ISMemDataImpl">
        <value name="userId">1</value>
        <value name="userName">Alice</value>
      </record>
      <record javaclass="com.wm.data.ISMemDataImpl">
        <value name="userId">2</value>
        <value name="userName">Bob</value>
      </record>
    </array>
  </record>
</IDataXMLCoder>
```

### String Arrays

```xml
<?xml version="1.0" encoding="UTF-8"?>
<IDataXMLCoder version="1.0">
  <record javaclass="com.wm.data.ISMemDataImpl">
    <array name="tags" type="value" depth="1">
      <value>tag1</value>
      <value>tag2</value>
      <value>tag3</value>
    </array>
  </record>
</IDataXMLCoder>
```

## Test Case Types

### 1. Success Tests
Test valid inputs with expected successful outputs.

**Naming:** `success_test1`, `success_test2`, etc.

**Example:**
```xml
<!-- success_test1-input.xml -->
<record javaclass="com.wm.data.ISMemDataImpl">
  <value name="num1">5</value>
  <value name="num2">3</value>
</record>

<!-- success_test1-result.xml -->
<record javaclass="com.wm.data.ISMemDataImpl">
  <value name="sum">8</value>
</record>
```

### 2. Error Tests
Test invalid inputs and error handling.

**Naming:** `error_test1`, `error_test2`, etc.

**Example:**
```xml
<!-- error_test1-input.xml -->
<record javaclass="com.wm.data.ISMemDataImpl">
  <value name="num1">abc</value>
  <value name="num2">3</value>
</record>

<!-- error_test1-result.xml -->
<record javaclass="com.wm.data.ISMemDataImpl">
  <value name="errorMessage">Invalid numeric input</value>
  <value name="sum">0</value>
</record>
```

### 3. Edge Case Tests
Test boundary conditions, null values, empty strings.

**Naming:** `edge_test1`, `edge_test2`, etc.

**Example:**
```xml
<!-- edge_test1-input.xml -->
<record javaclass="com.wm.data.ISMemDataImpl">
  <value name="num1">0</value>
  <value name="num2">0</value>
</record>

<!-- edge_test1-result.xml -->
<record javaclass="com.wm.data.ISMemDataImpl">
  <value name="sum">0</value>
</record>
```

### 4. Validation Tests
Test input validation logic.

**Naming:** `validation_test1`, `validation_test2`, etc.

## Test Coverage Guidelines

### Minimum Coverage
Every service should have at least:
- ✅ 1 success test (happy path)
- ✅ 1 error test (error handling)

### Comprehensive Coverage
For production services, include:
- ✅ Multiple success scenarios
- ✅ Error handling for each error type
- ✅ Edge cases (null, empty, boundary values)
- ✅ Validation tests for each input parameter

### Coverage by Service Type

#### FlowService
- Success paths for all branches
- Error handling (TRY/CATCH blocks)
- Conditional logic (IF/SWITCH)
- Loop iterations (empty, single, multiple items)

#### Adapter Service
- Valid query results
- Empty result sets
- Database connection errors
- Invalid parameters

#### FlatFile Schema
- Valid file parsing
- Invalid format handling
- Missing fields
- Extra fields

## Test Naming Conventions

### Test Case Names
- Use descriptive, lowercase names with underscores
- Include test type prefix: `success_`, `error_`, `edge_`, `validation_`
- Add sequence number: `success_test1`, `success_test2`

**Examples:**
- `success_test1` - First success scenario
- `error_invalid_input` - Error with invalid input
- `edge_empty_string` - Edge case with empty string
- `validation_required_field` - Validation of required field

### File Names
- Match test case name exactly
- Add suffix: `-input.xml` or `-result.xml`

**Examples:**
- `success_test1-input.xml`
- `success_test1-result.xml`
- `error_invalid_input-input.xml`
- `error_invalid_input-result.xml`

## Generation Workflow

### Step 1: Analyze Service
- Identify input parameters
- Identify output parameters
- Identify error handling logic
- Identify conditional branches

### Step 2: Determine Test Cases
- List success scenarios
- List error scenarios
- List edge cases
- List validation scenarios

### Step 3: Generate Test Suite XML
- Create TestSuite with descriptive name
- Add TestCase for each scenario
- Reference input/result files

### Step 4: Generate Input Files
- Create input XML for each test case
- Use valid IDataXMLCoder format
- Include all required parameters

### Step 5: Generate Result Files
- Create result XML for each test case
- Include expected output values
- Include error messages for error tests

## Best Practices

### 1. Descriptive Test Names
✅ Good: `success_add_positive_numbers`
❌ Bad: `test1`

### 2. Complete Coverage
- Test all code paths
- Test all error conditions
- Test boundary values

### 3. Clear Expected Results
- Be specific about expected values
- Include all output fields
- Document expected error messages

### 4. Maintainable Tests
- Keep tests simple and focused
- One scenario per test case
- Use meaningful test data

### 5. Documentation
- Add clear descriptions to test cases
- Document test purpose
- Explain expected behavior

## Troubleshooting

### Invalid XML Format
- Ensure proper XML declaration
- Verify IDataXMLCoder version="1.0"
- Check record javaclass attribute

### Test Execution Failures
- Verify service exists in specified folder
- Check input parameter names match service signature
- Ensure expected output matches actual service output

### File Not Found Errors
- Verify file names match exactly (case-sensitive)
- Check files are in same directory as TestSuite XML
- Ensure `-input.xml` and `-result.xml` suffixes

---

## Summary

Unit testing in webMethods uses:
- XML-based test suites
- IDataXMLCoder format for data
- File-based input/output definitions
- Integration Server test framework

Follow this guide to create comprehensive, maintainable test suites for all generated services.
